## 1. Executive Summary

Milestone **UI-3** delivers the Investigation Workspace for the Production Incident Intelligence System (PIIS — Telecom Edition). In critical national telecommunications infrastructure, an AI decision-support interface introduces severe operational risks if it claims unwarranted certainty, conceals conflicting network metrics, executes unauthorized configuration commands, or leaks authentication credentials.

This report evaluates and verifies the security boundaries, operational guardrails, and epistemic integrity implemented in UI-3.

---

## 2. Operational Safety Boundaries & Read-Only Posture

### Invariant: Zero Autonomous Remediation
The Investigation Workspace is strictly an **observational and diagnostic decision-support interface**.

1. **No Outbound Network Mutations:**
   - The workspace contains **zero** commands, APIs, or controls capable of modifying live telecommunications elements (e.g., eNodeB/gNodeB power levels, router BGP peering tables, UPF tunnel endpoints, or IMS CSCF routing rules).
   - No CLI terminal, SSH runner, or Netconf/YANG executor is exposed to the browser.
2. **Explicit Human Review Requirement:**
   - Every diagnostic recommendation generated by the RAG/runbook engine displays an unambiguous `HUMAN APPROVAL REQUIRED` declaration.
   - For `DISRUPTIVE_AUDIT` actions (e.g., cell barring, RF carrier shutdown), the workspace renders a high-visibility amber warning box declaring that remediation actions must be scheduled through standard telecom change management boards (CAB) and approved within the enterprise ITSM system.
3. **Immutable Reviewer Audit Trail:**
   - Sign-offs and review notes displayed in `RecommendationCard.tsx` are read directly from backend audit records (`reviewed_by`, `review_timestamp`, `review_notes`), preventing unilateral modification by unauthorized operators.

## 3. Epistemic Taxonomy & Truth Integrity

PIIS enforces a rigorous 6-tier epistemic taxonomy to eliminate AI overconfidence and prevent cognitive bias among NOC operators:

```
+-------------------------------------------------------------------------------+
|                      PIIS EPISTEMIC TAXONOMY TIERS                           |
+-------------------------------------------------------------------------------+
| Tier 1: DETERMINISTIC_VERIFIED | Merkle audit proofs, cryptographic hashes   |
| Tier 2: HEURISTIC_PREDICTION   | IsolationForest scores, ML hypothesis ranks |
| Tier 3: RAG_RETRIEVAL          | Telecom standard operating procedures (SOP) |
| Tier 4: UNVERIFIED_SOURCE      | External third-party monitoring feeds       |
| Tier 5: SYNTHETIC_EVALUATION   | Benchmarking and stress-test datasets       |
| Tier 6: OPERATOR_ASSERTION     | Human NOC engineer review notes             |
+-------------------------------------------------------------------------------+
```

### Specific Epistemic Enforcements in UI-3:
1. **Confidence Proxies vs Ground Truth:**
   - Candidate hypotheses are labeled **Heuristic Confidence Proxies** (e.g., `Confidence: 85.0%`).
   - The workspace explicitly forbids presenting hypotheses as confirmed root causes. Tooltips and mathematical rationales clearly explain that scores represent mathematical probability densities, not guaranteed physical states.
2. **Mandatory Contradictory Signal Display:**
   - If telemetry contradicts a leading hypothesis (e.g., normal optical power reported during a suspected fiber cut), the UI highlights the contradiction in rose badges and surfaces the contradictory signal directly inside the hypothesis card.
   - Contradictory evidence cannot be hidden or suppressed by the ranking engine.
3. **Stale Evidence Threshold (>3600s):**
   - In dynamic telecom topologies, telemetry older than 1 hour can misdiagnose transient issues.
   - The workspace automatically flags any evidence observed more than 3600 seconds prior with an alert badge: `STALE SIGNAL (> 1 hr old)`.
4. **Safe Abstention States:**
   - If the backend flags `is_sufficient: false`, the workspace presents a prominent warning banner with an itemized checklist of missing diagnostic telemetry, advising the engineer to abstain from high-risk intervention until additional probes are gathered.

## 4. Authentication, Session & Token Security

1. **In-Memory Credential Management:**
   - PIIS strictly maintains bearer tokens in private React memory via `AuthContext.tsx`.
   - **No token is ever written to `localStorage` or `sessionStorage`**, preventing XSS token exfiltration attacks.
2. **Volatile Session Fallback:**
   - In demo/development modes, authentication states use non-persistent memory holders that clear automatically on window refresh or tab destruction.
3. **Authorization Header Isolation:**
   - Outbound HTTP requests in `src/api/client.ts` attach the bearer token exclusively to configured `/api/v1/` endpoints.
   - Cross-origin request forgery is prevented by strict CORS configuration and read-only HTTP methods.

---

## 5. Defensive Rendering & Injection Prevention

1. **Unsanitized Payload Protection:**
   - Raw metadata payloads from upstream network elements (e.g., SNMP traps, syslog messages, Netflow records) can contain unexpected control characters, format string attempts, or malicious script tags.
   - All raw metadata in `EvidenceRegisterCard.tsx` is rendered using React's safe JSX encoding inside `<pre className="font-mono text-xs">` containers. `dangerouslySetInnerHTML` is strictly prohibited across the entire frontend codebase.
2. **Defensive Array & Object Inspection:**
   - The workspace handles malformed or partially populated backend payloads defensibly. Every array access (`hypotheses`, `evidence`, `recommendations`, `contradictions`) uses `Array.isArray()` fallbacks to prevent client-side JavaScript crashes if upstream payloads deviate.
3. **Structured Error Trapping:**
   - Upstream 500, 502, or 504 gateway failures are caught cleanly by `ErrorState.tsx`, displaying sanitized error descriptions without leaking internal Python tracebacks or infrastructure credentials to the end user.

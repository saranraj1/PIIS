## 1. Executive Summary & Verification Ledger

Milestone UI-5 successfully delivers the **Human Review Hub**, establishing an evidence-grounded human review interface at `/human-review`. The hub enables authorized human network operators to inspect recommendations generated by PIIS diagnostic pipelines, examine supporting telemetry and alarm evidence, review ranked root-cause hypotheses, detect contradictions and incomplete telemetry windows, and record human decisions (`APPROVED` or `REJECTED`) with cryptographic audit integrity.

Every design principle and operational safety boundary established across UI-0 through UI-4.1.1 is strictly enforced:
- **Zero Automated Remediation:** PIIS is strictly read-only decision support. Human approval never authorizes PIIS to execute production changes, CLI commands, network mutations, or ticket modifications.
- **Server-Side Identity Attestation:** Reviewer identity is extracted strictly from verified token claims in server-side authentication context (`require_human_operator`). Client-side operator spoofing attempts in request bodies are ignored.
- **Service Principal Lockout:** Automated service accounts, CI/CD runners, and bots are categorically barred from signing review decisions (`HTTP 403 Forbidden`).
- **Cryptographic Audit Notarization:** Decisions and operator technical rationale notes are canonicalized via RFC 8785 JSON Canonicalization Scheme (JCS), hashed with SHA-256, signed with HMAC-SHA256, and appended to the immutable audit ledger.
- **Terminal Replay Lockout:** Decisions on already-terminal recommendations are rejected (`HTTP 409 Conflict`).
- **Epistemic Integrity:** Recommendations remain strictly classified as `[RECOMMENDATION]`, and approved actions become `[HUMAN-APPROVED DECISION]`. Neither status promotes a recommendation to a `[CONFIRMED ROOT CAUSE]`.

## 2. Answers to Backend Review Capability Audit

Based on the audit documented in `docs/ui/UI5_REVIEW_API_CAPABILITY_MATRIX.md`, here are the answers to the 8 core operational questions:

### 1. Does the backend already support human review and approval workflows?
**Yes.** The backend possesses an existing human approval engine in `src/piis/investigation/approval.py` (`HumanApprovalWorkflow` and `ApprovalStatus`), integrated into the REST API at `POST /api/v1/incidents/{incident_id}/reviews` and `GET /api/v1/incidents/{incident_id}/reviews`.

### 2. What exact review decisions are supported?
- `APPROVED`: Authorized human operator endorses the diagnostic recommendation.
- `REJECTED`: Authorized human operator rejects the diagnostic recommendation with documented technical rationale.
- *Unsupported Decisions:* `REQUEST_MORE_EVIDENCE` is **not** an existing backend state machine transition. Submitting any string other than `APPROVED` or `REJECTED` results in `HTTP 400 Bad Request`. Operators requiring additional evidence reject the action with notes or defer action until additional telemetry is collected.

### 3. How is the reviewer identity determined?
Reviewer identity is strictly extracted from verified JWT claims in the server-side authentication dependency `require_human_operator` (`src/piis/api/dependencies.py`). The token's `operator_id`, `sub`, or username is bound directly to the audit entry. The API request schema `ReviewSubmissionRequest` intentionally does **not** accept an `operator_id` field; any client-provided identity parameters are ignored.

### 4. Are review notes cryptographically bound to the decision?
**Yes.** Under audit ledger schema v2.0, the reviewer's technical rationale notes are incorporated directly into the RFC 8785 canonical JSON payload alongside the recommendation ID, incident ID, reviewer ID, timestamp, and decision. The entire payload is hashed with SHA-256 and signed with HMAC-SHA256 (`notes_cryptographically_covered = True`). Any post-hoc tampering of the notes invalidates the cryptographic receipt.

### 5. Can decisions be overwritten or replayed?
**No.** The underlying state machine enforces strict immutability. Attempting to approve or reject an already-terminal recommendation (`APPROVED` or `REJECTED`) raises an `IllegalStateTransitionError`, mapped by FastAPI to `HTTP 409 Conflict`.

### 6. Where are review records persisted?
Review records are persisted in two coordinated locations:
1. In-memory recommendation registry inside `HumanApprovalWorkflow` (fast lookup, queue indexing, state transitions).
2. Append-only cryptographic audit ledger (`src/piis/audit/ledger.py`), backed by disk (`data/audit/audit_log.jsonl`) with RFC 8785 canonical hashing and monotonic sequence checkpoints.

### 7. How are review decisions retrieved?
- Single incident review history: `GET /api/v1/incidents/{incident_id}/reviews` returns all notarized review receipts for that incident.
- Aggregated operational queue: `GET /api/v1/incidents/reviews/queue` returns all registered recommendations across incidents with filtering by status (`PENDING_REVIEW`, `APPROVED`, `REJECTED`), domain (`RAN`, `CORE`, `TRANSPORT`), and risk tier (`READ_ONLY_SAFE`, `LOW_OBSERVABILITY`, `DISRUPTIVE_AUDIT`, `HIGH_RISK_MANUAL`).

### 8. What happens when an approval is recorded?
Recording an approval:
1. Transitions the recommendation status from `PENDING_REVIEW` to `APPROVED`.
2. Records the authorized operator identity, UTC timestamp, and technical rationale notes.
3. Computes the RFC 8785 canonical hash and HMAC-SHA256 signature.
4. Emits a tamper-evident cryptographic receipt (`RCPT-...`, sequence number, canonical entry hash).
5. **DOES NOT** execute network changes, CLI commands, script automation, or ticket closures.

## 5. Security & Safety Boundary Disclosures

1. **Strictly Read-Only Telecom Decision Support:** PIIS does not execute network actions, configure network elements, execute CLI commands, or mutate ITSM tickets. Approving a recommendation notarizes human operator intent into the audit ledger for external NOC execution.
2. **Explicit Contradiction Surface:** If conflicting evidence or missing telemetry exists, the Human Review Hub surfaces high-contrast warning alerts. These alerts are never hidden or suppressed.
3. **No Automated Approvals:** Service principals, automated daemons, and background workers are strictly blocked from signing review decisions.
4. **Permanent Audit Record:** Review decisions are tamper-evident, RFC 8785 canonically hashed, HMAC signed, and monotonic checkpoint anchored.
5. **No Epistemic Inflation:** A recommendation remains a recommendation until approved by a human operator, at which point it becomes a human-approved decision. It is never automatically promoted to a confirmed root cause.

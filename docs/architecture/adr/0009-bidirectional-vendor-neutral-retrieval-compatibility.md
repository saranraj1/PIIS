# ADR-0009: Bidirectional Vendor-Neutral Retrieval Compatibility and Prose Bleed Elimination

- **Status:** Accepted
- **Decision:** Establish bidirectional vendor compatibility rules in `MetadataFilter`: generic standard runbooks tagged with `GENERIC_3GPP` or `MULTI_VENDOR` are bidirectionally compatible with vendor-tagged incidents (such as `ERICSSON`, `NOKIA`, `HUAWEI`, `CISCO`, `JUNIPER`, `ZTE`). Conversely, proprietary vendor runbooks (e.g., Cisco-specific SOPs) are strictly isolated and cannot match queries for other vendors or generic incidents. Missing chunk vendor metadata fails closed (no silent compatibility). In `IncidentInvestigationEngine._extract_vendor()`, enforce strict metadata precedence: structured fields (`metadata.vendor`, `incident.equipment_vendor`) override prose text. Contextual mentions of operational management tools and client software (e.g., `Cisco AnyConnect`, `AnyConnect VPN`, `Nokia NetAct EMS`, `Ericsson ENM`, `Huawei U2000`, `Wireshark`, `Webex`) are filtered out to prevent prose bleed from poisoning retrieval filters. Network element ID prefixes (`ERIC-`, `NOK-`, `CISCO-`, `JUN-`, `HUA-`, `ZTE-`) are recognized as valid element indicators, and ambiguous vendor text safely abstains to `None`.
- **Context:** The M5.1 independent revalidation identified `FIND-M5.1-003`, where a technician connecting via "Cisco AnyConnect VPN" to triage an Ericsson cell site caused retrieval filters to bind to Cisco, rejecting approved 3GPP runbooks and generating false-positive vendor contradictions. Furthermore, generic 3GPP runbooks were rejected when matched against vendor-tagged incidents due to unidirectional filter logic.
- **Consequences:** Restores full runbook retrieval for vendor-tagged operational incidents using standard 3GPP procedures, prevents conversational prose bleed from subverting diagnostic hypotheses, and enforces strict isolation between proprietary vendor architectures.
